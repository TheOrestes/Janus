B2c: Queues, Fences, Frames in Flight

Janus learning notes. How the CPU hands work to the GPU, how it knows the GPU is done, and why we keep more than one frame in flight.

0. The restaurant version

Before the API names, here is the whole idea as a restaurant.

  • You are the waiter (CPU). You write orders on cards. The cook is the GPU. The cook cooks exactly what the cards say, in order.
  • The order slot is the queue. You drop the cards in and walk away. You do not stand there while the food cooks.
  • The scoreboard on the wall is the fence. It shows one number. After each batch of cards you add one more card: "when you get here, write 4 on the scoreboard". Because the cook works in order, a 4 on the board means everything before that card is cooked. To find out, you glance at the board. If it isn't there yet, you take a nap and ask to be woken when it shows 4.
  • The trays are the command allocators. The cards sit on a tray, and the cook reads them off that tray while cooking. With one tray, you and the cook take turns waiting for each other. With two trays, you fill tray B while the cook works from tray A.
  • The tray rule: before you wipe a tray and write new cards on it, check that the board has reached the number you wrote on that tray's last batch. Otherwise you wipe cards the cook is still reading.
  • Closing time is shutdown. You do not take the stove away while the cook is still cooking. Wait for the last number, then clean up.

1. The CPU and GPU are two timelines

  • Calling a D3D12 function records or submits work. It does not run it. The GPU runs it later, on its own clock.
  • So the CPU can be several frames ahead of the GPU. Anything the GPU is still reading (a buffer, a command allocator) must not be changed or freed by the CPU until the GPU is finished with it.
  • The tool for knowing that is the fence.

2. The objects, in the order work flows

ObjectRole
ID3D12CommandAllocatorThe memory the commands are recorded into. Reset only when the GPU is done with every list recorded in it.
ID3D12GraphicsCommandListThe recorder. Cheap to reset and reuse right after Close and ExecuteCommandLists.
ID3D12CommandQueueThe GPU's inbox. ExecuteCommandLists appends closed lists to it. Types: Direct (everything), Compute, Copy.
ID3D12FenceA 64-bit counter the GPU can raise. The CPU asks "has it reached N yet?".
IDXGISwapChainA ring of back buffers plus Present, which tells the display to show the next one.

The allocator is the one people trip on. A list is reusable immediately, but its allocator is not: the GPU reads the allocator's memory while it executes. That is why we need one allocator per frame in flight.

3. The fence

fenceValue (CPU side, we own it) : 0 -> 1 -> 2 -> 3 ... queue->Signal(fence, N) : "after everything before this, set the counter to N" fence->GetCompletedValue() : what the GPU has reached so far fence->SetEventOnCompletion(N, e) : raise an OS event when the counter reaches N WaitForSingleObject(e) : CPU sleeps until then
  • Signal is itself a queue command. It lands after the frame's work, so reaching N means all earlier work is done.
  • Check GetCompletedValue() >= N first. If it is already true, do not wait at all.
  • Fence values only ever increase. Never reuse one.

Setup and one frame, step by step

Setup runs once: the device creates every object, and the list is closed at the end so the frame loop can always start with Reset. One frame is the same steps every time: check, optional wait, reset, record, submit, present, signal. The wait only runs when the GPU is still using this slot. Use the tabs to switch, and Next or Play to step through.

So there is no special first frame in the code. The only difference is whether the fence check has to wait. With 2 frames in flight, frames 0 and 1 never wait and frame 2 is the first that can. The B2c code uses one allocator and waits for the GPU every frame, so there frame 1 is already a reuse.

4. Frames in flight

  • One frame in flight: the CPU records frame N, the GPU runs it, the CPU waits for it, and only then records N+1. Simple, but one side is always idle.
  • Two or three in flight: the CPU records N+1 while the GPU runs N. Each slot owns its own allocator (and later its own constant buffers), because the GPU may still be reading slot N while the CPU works on N+1.
  • Before reusing slot i, wait until the fence value we signalled for that slot last time has been reached.
  • Janus will start with 2. More frames means more latency (input to screen) and fewer stalls.
frame loop, slot = frameIndex % 2: wait fence >= slotFence[slot] // GPU done with this slot's last use allocator[slot]->Reset(); list->Reset(allocator[slot]) record: barrier PRESENT->RENDER_TARGET, clear, barrier RENDER_TARGET->PRESENT Close; queue->ExecuteCommandLists swapchain->Present slotFence[slot] = ++fenceValue; queue->Signal(fence, slotFence[slot])

Which value does a reused slot wait for?

The value that slot was tagged with last time, not the value the new frame is about to signal. Frame 2 reuses slot 0, so it waits for 1, the value frame 0 signalled. Waiting for 3 would deadlock: 3 is only signalled after frame 2's own work, which has not been submitted yet.

5. The swapchain

  • A ring of N back buffers (we use 2, flip model: DXGI_SWAP_EFFECT_FLIP_DISCARD). Present hands the one we drew to the display and advances the ring.
  • GetCurrentBackBufferIndex() says which buffer to draw into this frame. It is not the same number as the frame-in-flight slot. Keep both indices.
  • Each back buffer needs a render target view (RTV) in a descriptor heap. We create the views once and index by back buffer.
  • Barrier round trip per frame: PRESENT to RENDER_TARGET before clearing, and back to PRESENT before Present (see B2b).
  • The swapchain is created from the queue, not the device. That is how it knows who will be presenting. It also needs the window's HWND, which is why we added GetNativeHandle on Window.
  • Resize, tearing and VSync options come later. Shutdown rule: wait for the GPU to go idle (signal, then wait on that value) before releasing anything it uses.

B3 then adds the per-slot allocators and the frames-in-flight loop from section 4. B2c can get away with a single allocator and a WaitIdle each frame, which is the "one frame in flight" case.
