B2a: Command queues, command lists, swapchain, RTVs

Janus learning notes. Theory, math and diagrams for chapter B2a.

1. Commands are recorded, not executed

  • The GPU runs asynchronously from the CPU. Calling Draw does not draw; it appends a command to a buffer. Nothing runs until the buffer is submitted to a queue.
  • So the CPU records frame N+1 while the GPU executes frame N. The GPU runs behind the CPU by up to the number of frames in flight.

The price of this overlap is latency. With F frames in flight, input-to-photon delay grows by about F frame times.

latency_extra ~= F * (1000 / refresh_hz) ms
Frames in flight (F)Extra latency at 60 Hz (16.67 ms/frame)
1about 16.7 ms
2about 33.3 ms
3about 50.0 ms

2. The three command objects

Think of a notebook. The allocator is the paper, the list is the pen, and the queue is the door the finished pages go through to reach the GPU.

ObjectJobKey calls
ID3D12CommandAllocatorOwns the memory the commands are stored in.Reset() frees all of it at once
ID3D12GraphicsCommandListThe interface you record through. Draw, ClearRenderTargetView and barriers append to the allocator's memory.Close() ends recording; Reset(allocator) starts again
ID3D12CommandQueueTakes closed lists and hands them to the GPU. Also signals fences.ExecuteCommandLists, Signal

A Draw call therefore never touches the queue. It writes bytes into the allocator's memory through the list. The queue only sees the work after you Close() the list and call ExecuteCommandLists.

The reset rules

  1. The list may be Reset() as soon as ExecuteCommandLists returns. The queue has already taken what it needs from it.
  2. The allocator may not. Submitting does not mean the GPU has finished. It may still be reading the allocator's memory, and resetting would free that memory under it.
  3. The allocator is safe to reset only after a fence shows the GPU has finished that frame. The queue signals the fence after the submit; the CPU compares the fence's completed value with the frame's value.
  4. One allocator can back only one list that is recording at a time.

How many allocators?

One per frame in flight. Each frame records into its own allocator, so recording the next frame never disturbs memory the GPU is still reading.

FrameAllocatorBefore reusing it
0A(first use)
1B(first use)
2Await until the fence says frame 0 is done, then reset A
3Bwait until the fence says frame 1 is done, then reset B

With 2 frames in flight that is 2 allocators. With 3 frames in flight it is 3.

The queue type is DIRECT (graphics, compute and copy) for now. COMPUTE and COPY queues exist for separate work. Janus uses DIRECT only.

3. Swapchain (flip model)

A swapchain is a small ring of images. The window shows one of them while the GPU draws into another. In the flip model, DXGI_SWAP_EFFECT_FLIP_DISCARD, the display switches which buffer it reads from instead of copying pixels. That makes it cheap.

  • At any moment each buffer has exactly one role: on screen, ready and waiting, or being rendered into.
  • Present() advances the roles by one step around the ring.
  • GetCurrentBackBufferIndex() returns which buffer is the one to render into this frame. We use that index to pick the matching RTV (next section).
  • The minimum is 2 buffers. Janus uses 3, so the GPU is less likely to wait for the display.
  • The swapchain needs the window handle (HWND). GLFW provides it through glfw3native.h (glfwGetWin32Window), which is why Window gets a getter.

Memory cost

RGBA8 means 4 bytes per pixel (one byte each for red, green, blue and alpha). One buffer costs width x height x 4 bytes, and the swapchain holds three of them.

bytes_per_buffer = width * height * 4
total = bytes_per_buffer * buffer_count
ResolutionPer bufferThree buffers
1280 x 7203,686,400 B (3.52 MiB)11,059,200 B (10.55 MiB)
1920 x 10808,294,400 B (7.91 MiB)24,883,200 B (23.73 MiB)

MiB divides by 1,048,576 (220). MB divides by 1,000,000, which gives a slightly larger number for the same bytes: 24,883,200 B is 23.73 MiB or 24.88 MB.

4. RTVs and descriptor heaps

The GPU does not draw into a texture directly. It draws through a render target view (RTV), a small record that says "treat that texture as a render target, with this format and this mip level". RTVs are stored in a descriptor heap, which is simply an array of descriptors.

  • The heap type is RTV. RTV and DSV heaps are never shader-visible, so the CPU creates and uses them directly.
  • We create one RTV per back buffer, once at startup. For 3 buffers the heap has 3 slots.
  • Each frame, the back buffer index from the swapchain picks the slot.

Finding slot i

Slots are packed one after another, but the size of one slot is up to the driver. So you ask the device for it and step from the heap's start:

increment = device->GetDescriptorHandleIncrementSize(D3D12_DESCRIPTOR_HEAP_TYPE_RTV)
handle(i) = heapStart + i * increment

Worked example. Suppose the driver reports an increment of 32 bytes (an illustrative value; yours may differ). Then:

SlotBack bufferHandle
00heapStart
11heapStart + 32
22heapStart + 64

The size differs between GPU vendors and driver versions. A hardcoded number would work on one machine and point into the wrong place on another, so the code always queries it once and reuses the result.

5. What B2 builds

Command queue, swapchain (3 buffers, flip-discard), RTV heap with 3 RTVs, and a list that clears the current back buffer, then Present. The barrier that makes the buffer writable (Enhanced Barriers) is lesson B2b.
