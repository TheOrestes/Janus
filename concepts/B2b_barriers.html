B2b: Barriers (Enhanced Barriers)

Janus learning notes. Why barriers exist, what the three fields mean, and the Agility SDK needed to use them.

1. Why a barrier exists at all

  • The GPU is not one processor reading one memory. It is many units (raster, shader cores, copy engines, display) with their own caches, running in parallel and often out of order.
  • Submitting command A then command B does not mean B starts after A finishes. Without a rule, B can start while A is still writing.
  • A barrier is that rule. It tells the driver three separate things, and mixing them up is the usual source of confusion.
QuestionConcernWhat the hardware does
When may the later work start?Scheduling (sync)Stalls the later stage until the earlier stage has finished
Whose writes must the later work see?Caches (access)Flushes the writer's cache, invalidates the reader's cache
How are the texels arranged in memory?LayoutMay decompress or re-tile the texture (for example color compression used by the render target path but not by the display engine)

The third row is why textures need more than a fence. The same bytes can be stored in different internal formats depending on who will use them next. Presenting needs a plain layout the display engine can scan out; rendering is happy with a compressed, tiled one.

2. Legacy states versus Enhanced Barriers

Legacy D3D12 had one combined idea: D3D12_RESOURCE_STATES. A single value such as RENDER_TARGET meant sync, cache and layout all at once, and the driver guessed the rest.

LegacyEnhanced
VocabularyOne state enumSeparate sync, access and layout fields
CommandResourceBarrierBarrier (command list 7+)
PrecisionDriver infers the stages and caches involved, often over-syncingYou state the exact stages and accesses
Vulkan mappingLossyClose to 1:1 with VkDependencyInfo

Janus targets Vulkan later, so it uses Enhanced Barriers from the start. The three fields map directly:

D3D12 EnhancedVulkan 1.3
SyncBefore / SyncAftersrcStageMask / dstStageMask
AccessBefore / AccessAftersrcAccessMask / dstAccessMask
LayoutBefore / LayoutAfteroldLayout / newLayout

3. The three barrier types

Barriers are submitted in groups, one group per type, in a single Barrier(numGroups, groups) call on ID3D12GraphicsCommandList7.

TypeStructTargetsHas layout?
GlobalD3D12_GLOBAL_BARRIERAll memory, no specific resourceNo
BufferD3D12_BUFFER_BARRIEROne bufferNo
TextureD3D12_TEXTURE_BARRIEROne texture and a subresource rangeYes

Swapchain back buffers are textures, so B2 uses only texture barriers.

The texture barrier fields

FieldMeaning
SyncBefore, SyncAfterWhich pipeline stages must finish before / may start after, for example RENDER_TARGET or ALL. NONE means nothing to wait for or nothing waits.
AccessBefore, AccessAfterHow the texture was / will be touched, for example RENDER_TARGET. NO_ACCESS means untouched on that side.
LayoutBefore, LayoutAfterThe layout it is in now and the layout it must be in next, for example PRESENT then RENDER_TARGET.
pResource, SubresourcesWhich texture, and which mips/slices. A back buffer has one subresource.
FlagsOptional DISCARD: the old contents are not needed, so no data needs preserving during the layout change.

The rule of thumb: Before describes the previous user, After describes the next user. Get them reversed and you get hazards the debug layer will flag.

4. The swapchain example

Each frame the back buffer is used twice, by two different "users": the renderer and the display. Each handoff is one barrier.

BarrierSyncAccessLayout
Before drawingNONE to RENDER_TARGETNO_ACCESS to RENDER_TARGETPRESENT to RENDER_TARGET
Before presentRENDER_TARGET to NONERENDER_TARGET to NO_ACCESSRENDER_TARGET to PRESENT
  • Back buffers are created in the PRESENT layout, so the first barrier of the first frame is already correct.
  • Sync NONE on the "present" side: Present is not a command-list stage. The ordering with the display is handled by the swapchain itself, so the barrier only has to make the render target writes finished and the layout correct.
  • The Present-time barrier is what flushes the render target cache and puts the texture in the display-friendly layout.

5. The Agility SDK

  • Enhanced Barriers are not in the D3D12 runtime that ships with Windows. They come from the Agility SDK, a side-by-side runtime (D3D12Core.dll) that your exe can load instead of the system one.
  • Reason: new D3D12 features can ship without waiting for a Windows update. The cost is a few deployment rules.

Deployment rules

  1. Get the NuGet package Microsoft.Direct3D.D3D12 (a zip). Use a version that includes Enhanced Barriers (1.608 or later).
  2. Copy D3D12Core.dll and d3d12SDKLayers.dll (debug layer) into a D3D12\ folder next to the exe.
  3. Export two symbols from the exe so the loader knows which runtime to pick:
extern "C" { __declspec(dllexport) extern const UINT D3D12SDKVersion = <sdk version>; } extern "C" { __declspec(dllexport) extern const char* D3D12SDKPath = ".\\D3D12\\"; }
  1. The version number must match the package exactly. A mismatch makes D3D12CreateDevice fail or silently use the system runtime.
  2. Even with the SDK, the GPU driver must support Enhanced Barriers. Query it at startup:
D3D12_FEATURE_DATA_D3D12_OPTIONS12 o12 = {}; device->CheckFeatureSupport(D3D12_FEATURE_D3D12_OPTIONS12, &o12, sizeof(o12)); // o12.EnhancedBarriersSupported must be TRUE

Janus handles this like the assets: a CMake post-build step copies the DLLs into D3D12\ beside the exe, and the two exports live in the Sandbox (or the RHI) translation unit.

6. What B2b builds

  • Vendor the Agility SDK and wire the CMake copy step.
  • Add the two exports; verify EnhancedBarriersSupported and log it.
  • Query ID3D12GraphicsCommandList7 and write a small helper that emits a texture barrier for the back buffer.
  • Used for real in B2c: PRESENT to RENDER_TARGET, clear, RENDER_TARGET to PRESENT.
